# tt

Таск-трекер над markdown-vault. Источник правды — файлы `tasks/<project>/*.md`
с YAML-фронтматтером; `tt` их читает и правит по одному ключу за раз.

Заменяет файловые Kanban-доски Obsidian и обратный синк на них: доска перестаёт быть
файлом и становится представлением, которое строится из фронтматтера в момент показа.
Синхронизировать нечего — второго хранилища статуса не существует.

## Сборка

Веб-бандл (`web/dist`) вшивается в бинарник через `go:embed`, поэтому фронт
собирается **первым**:

```bash
cd web && npm install && npm run build && cd ..
go build -o tt.exe ./cmd/tt
```

Если пропустить `npm run build`, `go build` всё равно пройдёт — в git лежит
заглушка `web/dist/index.html` — но `tt serve` покажет её вместо настоящей
страницы. Обратный порядок тоже не спасает: `go build` вшивает то, что лежит
в `web/dist` **на момент сборки**, так что правки фронта без пересборки
бинарника не видны.

Go-зависимостей три: `gopkg.in/yaml.v3`, `github.com/fsnotify/fsnotify` и
`golang.org/x/sys` (транзитивная). На выходе один статический бинарник.

### Установщик Windows

`installer/tt.iss` — скрипт Inno Setup 6 (ставится через winget:
`winget install JRSoftware.InnoSetup`). Собирается **после** бинарника, тем же
`ISCC.exe`, что и весь остальной Inno Setup:

```bash
cd web && npm install && npm run build && cd ..
cd obsidian-plugin && npm install && npm run build && cd ..
go build -o tt.exe ./cmd/tt
"%LOCALAPPDATA%\Programs\Inno Setup 6\ISCC.exe" installer\tt.iss
```

Плагин собирается обязательно: `obsidian-plugin/main.js` — артефакт сборки, в git
его нет, а установщик кладёт его в поставку. Пропустишь шаг — `ISCC.exe` упадёт
на отсутствующем файле. Путь к `ISCC.exe` зависит от способа установки Inno
Setup: winget кладёт его в профиль пользователя, установщик с сайта по умолчанию
— в `C:\Program Files (x86)\Inno Setup 6\`.

Готовый `.exe` появляется в `installer/Output/` (в git не коммитится). Установщик
не требует прав администратора: каталог по умолчанию — в профиле пользователя,
PATH и автозагрузка правятся per-user (`HKCU\Environment`, `{userstartup}`).

Что спрашивает мастер: каталог установки, путь к vault (проверяется наличие
`tasks/`; если его нет, мастер предлагает создать структуру прямо на месте —
см. `tt scaffold` ниже — а отказ возвращает на выбор каталога, как раньше),
порт `tt serve` (предупреждает, если занят, но не блокирует),
галочки «добавить в PATH» и «запускать `tt serve` при входе» (обе включены
по умолчанию) и «поставить плагин Obsidian» (выключена по умолчанию — не у
всех Obsidian вообще стоит). Настройки установщик пишет через
`tt config set --vault --port`, а не правкой JSON напрямую.

Автозапуск сделан ярлыком в папке автозагрузки на VBS-скрипт
(`installer/tt-serve-hidden.vbs`), который поднимает `tt serve` через
`WScript.Shell.Run` со скрытым окном — без окна консоли и без прав
администратора. Регистрация через Планировщик заданий отклонена: в этом
проекте она уже требовала повышения прав и не прошла (см. `rules/`), а ярлык
в автозагрузке даёт тот же результат безо всяких прав.

Предложение создать структуру vault работает уже на шаге выбора каталога,
до того как файлы программы вообще скопированы в `{app}` — поэтому в
`[Files]` отдельной строкой (`Flags: dontcopy`) лежит вторая копия `tt.exe`,
которую мастер извлекает во временный каталог (`ExtractTemporaryFile`) и
вызывает как `tt.exe scaffold --vault ПУТЬ`. Сама логика создания — в `tt`
(`internal/taskop/scaffold.go`), установщик только спрашивает и зовёт команду.

Удаление снимает PATH, автозагрузку и ярлыки, но не трогает vault, файл
настроек (`%APPDATA%/tt/config.json`) и плагин внутри vault — это данные
пользователя, а не файлы программы.

**Установщик не подписан.** SmartScreen пометит его как «неизвестный
издатель» — это ожидаемо для инструмента, который ставят себе и коллегам по
прямой ссылке, а не публикуют массово. При первом запуске нужно нажать
«Подробнее» → «Выполнить в любом случае». Подпись кода стоит денег и не
настроена; ложной тревоги антивируса это не означает.

## Команды

```
tt list    [--vault ПУТЬ] [--project ИМЯ] [--status СТАТУС] [--json]
tt new     [--vault ПУТЬ] --project ИМЯ --title ТЕКСТ [--priority high|medium|low]
           [--effort 2h] [--depends-on ID,ID] [--spec ПУТЬ]
tt next    [--vault ПУТЬ] --project ИМЯ [--json]
tt claim   [--vault ПУТЬ] [--agent ИМЯ] ID
tt release [--vault ПУТЬ] ID
tt reset   [--vault ПУТЬ] ID
tt set     [--vault ПУТЬ] [--agent ИМЯ] ID КЛЮЧ [ЗНАЧЕНИЕ]
tt done    [--vault ПУТЬ] [--agent ИМЯ] [--result ТЕКСТ] ID
tt scaffold [--vault ПУТЬ] [--project ИМЯ] [--id-prefix ПРЕФИКС]
tt doctor  [--vault ПУТЬ] [--fix]
tt serve   [--vault ПУТЬ] [--port N] [--listen АДРЕС] [--agent ИМЯ] [--token ТОКЕН]
tt config show [--vault ПУТЬ] [--port N]
tt config set  [--vault ПУТЬ] [--port N]
```

Полный цикл выглядит так:

```bash
tt new --project myapp --title "Починить логин" --priority high   # → APP-042
tt next --project myapp                                           # что брать
tt claim APP-042                                                  # взять в работу
tt done --result "исправлено, тесты зелёные" APP-042              # закрыть
```

`tt done` сам снимает claim с замком и переводит в `ready` те таски, для которых
закрытая была последним живым блокером.

Путь к vault берётся из `--vault`, иначе из `TT_VAULT`, иначе из файла настроек
(`tt config`). Пути по умолчанию нет намеренно: молча писать в чужой каталог хуже,
чем потребовать один флаг, переменную или явную запись в файле настроек.

`--status` понимает исторические написания: `--status in-progress` находит и таски
с `status: in_progress`.

`tt set` меняет одно поле. Смена статуса дополнительно проставляет `completed`/`ready_at`
и снимает `claim` с замком по правилам схемы. Незнакомый ключ отклоняется: иначе опечатка
тихо добавила бы во фронтматтер мусорное поле.

`tt claim` берёт таску в работу: проверяет переход, ставит замок и пишет блок `claim`
с полями `agent`, `host`, `branch`, `started`. `host` — имя машины, `branch` — текущая
ветка репозитория проекта (поле `repo` в `projects/<project>.md`); репозиторий недоступен —
поле остаётся пустым, а не выдумывается. Повторный `claim` своим же агентом законен,
чужой — отклоняется.

`tt release` отдаёт таску обратно в `ready`, снимая claim и замок. `tt reset` расклинивает
залипшую таску после упавшей сессии: снимает замок и claim даже чужие и засчитывает
попытку в `attempts`. Замена `/work --reset`.

`tt scaffold` создаёт в каталоге ровно то, чего требует код: `tasks/`,
`templates/task-template.md`, `.task-tracker/schema.json` и один проект
(`projects/<имя>.md` с `id_prefix` и `next_id: 1`) — этого достаточно для
`tt new` без правок руками. Каталоги `daily/`, `weekly/`, `analytics/`,
`archive/` и `dashboard.md` — наследие Obsidian, код их не читает, и
`scaffold` их не создаёт. Существующие файлы не перезаписываются: чего нет —
создаётся, что есть — остаётся как было, и в выводе видно, что именно
сделано (`создано: …` / `уже было: …`) — повторный запуск на готовом vault
безопасен. `--project` по умолчанию — имя каталога vault, `--id-prefix` —
инициалы слов имени проекта (для `task-tracker` получится `TT`); оба можно
задать явно. Не путать со слеш-командой `/init` — та про онбординг
репозитория в трекер, а не про создание файлов внутри самого vault.

`tt doctor` без `--fix` только отчитывается. Починяемые проблемы помечены `*`.

`tt serve` строит индекс, следит за vault на изменениях и поднимает веб-доску по
HTTP (`GET /api/snapshot`, `GET /api/task/{id}`, `GET /api/events` — SSE,
`POST /api/task/{id}/status`) плюс отдаёт сам фронт из `web/dist`. Порт — из
`--port`, иначе из файла настроек, иначе встроенный дефолт `4173`; занят —
понятная ошибка вместо паники. Ctrl+C гасит и HTTP, и вотчер. Сама доска на
этом этапе — заглушка (заголовок и число тасок); полноценный UI — отдельная
задача.

## Файл настроек

`tt` помнит vault и порт `tt serve`, чтобы не повторять их флагами в каждой команде —
нужно это в первую очередь установщику: пока `tt` не читал настройки из файла, ему
было некуда записать выбранный при установке vault.

Хранится в `%APPDATA%/tt/config.json` (Windows: `os.UserConfigDir()` + `tt/config.json`) —
этот путь переживает переустановку `tt.exe`, в отличие от файла рядом с бинарником,
который слетел бы при обновлении. Путь переопределяется переменной `TT_CONFIG_PATH`
(используется тестами — они не касаются реального `%APPDATA%`).

Формат — тот же JSON, что и `schema.json`, заводить второй формат в проекте незачем:

```json
{ "vault": "D:/task tracker", "port": 4180 }
```

Отсутствие файла — не ошибка, команды работают как раньше. Битый JSON — ошибка
с указанием пути к файлу: молча откатываться к дефолту нельзя, иначе непонятно,
почему настройки не применились.

```bash
tt config set --vault "D:/task tracker" --port 4180   # неинтерактивно, для установщика;
                                                        # меняет только переданные поля
tt config show                                         # что действует сейчас и откуда
```

`tt config show` называет источник каждого значения (`флаг`, `переменная окружения`,
`файл настроек`, `значение по умолчанию`) — без этого разбираться, почему подхватился
не тот vault, пришлось бы гадать.

Порт отдельно решает проблему неразличимости: у флага `--port` уже есть встроенное
значение по умолчанию (`4173`), поэтому «флаг не передан» и «передан `--port 4173`»
неотличимы друг от друга простой проверкой значения. Решение — `fs.Visit` после
`fs.Parse`: он называет только реально переданные флаги, и именно этот признак
(а не само значение) решает, откуда брать порт.

## Гарантии записи

- Меняется **ровно один ключ** фронтматтера; остальные байты файла не трогаются.
  Закреплено тестом: diff после смены статуса — ровно одна строка.
- Никакого round-trip через YAML-библиотеку: она переставила бы ключи и потеряла пустые
  значения, превратив git-diff в мусор.
- Запись атомарна: временный файл в том же каталоге плюс `rename`.
- CRLF, BOM и порядок ключей сохраняются; значения с `": "` закавычиваются при записи.
- Правка идёт под замком `.locks/<ID>.lock` — тем же, что берут bash-агенты.

## Замок

`.locks/<ID>.lock` — **не мьютекс на время команды, а долгоживущий признак «таска
в работе»**, парный статусу `in-progress`. Ставится при взятии в работу, снимается при
уходе из него, переживает и команду, и процесс. Упавшая сессия оставляет замок —
авто-снятия нет намеренно, сброс ручной. `tt doctor --fix` убирает осиротевшие.

## Правила флоу

Живут в `<vault>/.task-tracker/schema.json`: статусы, порядок и подписи лейнов,
исторические написания, что проставлять при переходе и когда снимать claim. Этот файл —
общий контракт для будущей веб-доски и плагина Obsidian, поэтому добавленный лейн
появится на обеих досках без правки кода. Если файла нет, используется встроенная копия.

Полной матрицы переходов нет сознательно: перетаскивание карточки между лейнами законно
почти всегда. Стерегутся два случая — взять в работу таску с живыми `blocked_by`
и отобрать чужой claim.

## Состояние

**Все четыре этапа завершены.** Чтение и запись, полный жизненный цикл таски,
плагин Obsidian, веб-доска с доступом по локальной сети, слеш-команды всех четырёх
семейств агентов переведены на `tt`, замещённые bash-скрипты сняты.

От прежнего shell-ядра осталось два скрипта, и у обоих нет замены в `tt`:
`tt-resolve.sh` определяет vault и проект по `.task-tracker.json` текущего
репозитория, `tt-active.sh` держит маркер активной таски для statusline.

Файловых Kanban-досок больше нет: статус живёт только в поле `status:` таски,
а канбан рисуется на лету — плагином внутри Obsidian или веб-доской.

Замеры на живом vault из 1300 тасок:

| | |
|---|---|
| бинарник | 10.9 МБ |
| веб-бандл | 56 КБ JS + 6 КБ CSS |
| `tt serve` до первого ответа | 580–600 мс |
| снимок для браузера | 384 КБ |
| память процесса | 22 МБ RSS |

Рост бинарника с 5.0 МБ дал не бандл, а линкер: следом за `http.Server` подтягиваются
`crypto/tls`, `x509` и `http2`, даже когда TLS не используется.

Известные ограничения:

- `tt set X status in-progress` замок ставит, но блок `claim` не пишет: владельца
  фиксирует только `tt claim`.
- Таски с непарсящимся фронтматтером не видны ни на веб-доске, ни в плагине — их
  показывает `tt doctor`. В живом vault таких 31.
- `go test -race` на машине разработки недоступен: детектор гонок требует CGO,
  а `CGO_ENABLED=0` и нет C-компилятора.

## Тесты

```bash
go test ./... -count=1
go vet ./...
```

Смоук по живому vault (только чтение, копии правятся во временном каталоге):

```bash
TT_SMOKE_VAULT="D:/task tracker" go test ./internal/vault/ -run TestLiveVault -count=1 -v
```
