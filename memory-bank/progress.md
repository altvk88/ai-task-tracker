# Progress

## Working

Все четыре этапа завершены. Три интерфейса к одним и тем же markdown-файлам:
командная строка, доска внутри Obsidian, веб-доска в браузере.

**Ядро (`tt`), 45 задач проекта:**

- чтение фронтматтера, терпимое к историческим формам `verify` и `claim`;
- хирургическая запись: один ключ, атомарно, с сохранением CRLF, BOM и порядка ключей;
- блочная запись для `claim` через тот же путь замены строк;
- замок `.locks/<ID>.lock`, общий с прежними bash-агентами;
- guard'ы: нельзя взять в работу заблокированную и нельзя отобрать чужой claim;
- команды `list`, `new`, `next`, `claim`, `release`, `reset`, `set`, `done`, `doctor`, `serve`.

**Плагин Obsidian** — канбан из `metadataCache`, перетаскивание на pointer-событиях,
запись через `processFrontMatter`, то есть через API Obsidian, а не мимо него.

**Веб-доска** — снимок по HTTP, живое обновление по SSE, перетаскивание, панель таски,
страница «Пульс», доступ с телефона по локальной сети с токеном на запись. Тело таски
рендерится как markdown (`marked`, сырой HTML экранируется). Таски правятся и создаются
прямо с доски: `POST /api/task`, `/api/task/{id}/field`, `/api/task/{id}/body`;
конкурентная правка ловится по `version` (mtime) и отвечает 409, а не тихой перезаписью.

**Слеш-команды** всех четырёх семейств агентов (Claude, Codex, Gemini, Vibe) зовут `tt`.
Правила флоу живут в одной реализации вместо четырёх копий.

Замеры на 1300 тасках: обход vault ~125 мс, `tt serve` до первого ответа 580–600 мс,
снимок 384 КБ, память 22 МБ RSS. Бинарник вырос с 10.9 до 11.8 МБ: иконка ресурсом
и бандл 57 → 111 КБ после парсера markdown и редактора.

**Установщик Windows** — Inno Setup 6, `installer/tt.iss`: vault с проверкой и
предложением создать структуру, порт, PATH, автозапуск без окна консоли, ярлыки на
доску, плагин Obsidian опцией. Иконка приложения — в exe, установщике, ярлыках и
фавиконе доски.

**Установщик macOS (TT-057)** — `installer/macos/build.sh` кросс-компилирует
`darwin/arm64` и `darwin/amd64` (без Mac, CGO не используется) и собирает staging +
архивы; `installer/macos/install.sh` делает то же, что windows-версия: PATH через
`~/.zprofile`/`~/.bash_profile`, vault и порт через `tt config set`, `tt scaffold` по
запросу, автозапуск через `launchd` (`~/Library/LaunchAgents`) с согласия, плагин
Obsidian опцией по умолчанию выключенной. `uninstall.sh` не трогает vault/настройки.
Собрать `.pkg`/`.dmg` без Mac нельзя — `pkgbuild`/`hdiutil` существуют только там,
поэтому форма поставки — архив + скрипт. Homebrew-формула рассмотрена и отклонена
(README, раздел про macOS) — `brew install` не может провести диалог установки без
дублирования install.sh. Gatekeeper описан в README по аналогии со SmartScreen.
**Не проверено на живой macOS** — машины нет: Gatekeeper, `launchd`, правка профиля
шелла. Проверены только синтаксис (`bash -n`) и кросс-сборка бинарников.

**Инструкция по подключению агентов (TT-058)** — `AGENT-INTEGRATION.md` в корне
репозитория (тот же текст — раздел README «Подключение к Claude Code и Codex»):
куда класть слэш-команды Claude Code (`.claude/commands/` проектный или
`~/.claude/commands/` глобальный), что нужно Codex (`AGENTS.md` + `~/.codex/prompts/`,
только верхний уровень), разница между ними, как проверить подключение
(`tt config show` + `/tt-task ...` → файл в `tasks/<project>/`) и что делать, если не
подключилось. Примеры команд — `agents/claude/commands/` и `agents/codex/prompts/`
(`tt-task`, `tt-work`, `tt-done`), написаны заново под `tt` из PATH, а не скопированы
из `claude-global/`/`codex/` владельца — те содержат хардкод личного пути
(`D:/tt/tt.exe`) и лишние для публичного репозитория вещи (opencode, banner-хук),
которые нельзя было заносить в публикацию. Установщик Windows кладёт файл в `{app}`,
показывает на финальной странице мастера и в `[Run]` (галочка снята по умолчанию) и
даёт ссылку в меню Пуск через notepad.exe; установщик macOS копирует файл рядом с
бинарником и печатает путь к нему в конце install.sh. Логика `claude-global/install.sh`
в установщики не перенесена — они только показывают путь к инструкции, интеграцию с
`~/.claude`/`~/.codex` пользователь выполняет сам по написанному в файле.

## Deployed

Плагин выложен в раздаваемую версию `D:/task-tracker-agent/obsidian-plugin/` вместе

## Дефекты планов, найденные исполнителями

Больше десятка. Самые дорогие:

1. Замок трактовался как мьютекс команды (`defer unlock()`), хотя это долгоживущий признак
   «таска в работе» — с кодом плана `in-progress` таски остались бы без замков.
2. `needsQuote` проверяла кавычку и бэкслеш только в первом байте значения.
3. Требование `-race` в обязательном прогоне при отсутствующем C-компиляторе.
4. Комментарий обещал экономию чтения, которой код не делал, и завышал объём vault впятеро.
5. Флаг перетаскивания залипал после `pointercancel` и съедал следующий клик.
6. `Promotable` промоутит всех кандидатов, а не только разблокированных этим закрытием —
   на живых данных это задело бы постороннюю таску.
7. План этапа 4 писался без осмотра `codex/`, `.gemini/` и `.vibe/`: снос скриптов
   сломал бы три набора команд из четырёх.

Вывод, закреплённый практикой: код в плане — черновик, а не эталон. Планы этапов 3 и 4
писались требованиями и контрактами, и это дало заметно лучший результат.
