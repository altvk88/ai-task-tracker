# TT Board — плагин Obsidian

Канбан-доска задач прямо из фронтматтера. Файлов досок не существует: доска строится
из `app.metadataCache` при каждой отрисовке, поэтому синхронизировать нечего.

Заменяет прежнюю связку «Kanban-плагин + файлы досок + вотчер обратного синка», где
статус таски хранился в двух местах и они регулярно расходились.

## Сборка и установка

```bash
npm install
npm run build
cp main.js manifest.json styles.css "<vault>/.obsidian/plugins/tt-board/"
```

Затем включить «TT Board» в Settings → Community plugins. После обновления файлов
плагин нужно перезагрузить: тумблер выключить-включить либо `Ctrl+P` →
«Reload app without saving».

## Что умеет

- Лейны из `<vault>/.task-tracker/schema.json` — того же файла, что читает `tt`.
  Пустые лейны сохраняются, чтобы доска не прыгала под руками.
- Таска с неизвестным статусом не теряется: получает собственный лейн в конце.
- Фильтр по проекту и поиск по ID и заголовку.
- Перетаскивание карточек на pointer-событиях: работает мышью и пальцем.
- Клик по карточке открывает файл таски в соседней панели.
- Живое обновление: правка таски агентом из терминала доезжает до доски сама.

Карточка показывает ID, заголовок, приоритет цветной полосой слева, `effort`,
метку `◉` у занятой таски и `🔒` при живых блокерах — с подсказкой, каких именно.

## Правила

Совпадают с Go-реализацией по построению: оба клиента читают одну схему.

- Статусы нормализуются через `aliases` (`in_progress` → `in-progress`).
- Нельзя взять в работу таску с живыми `blocked_by` или занятую другим.
- Уход из `in-progress` разрешён всегда — иначе не разблокировать таску, залипшую
  после упавшей сессии. Таких следов в vault было 81 штука.
- При уходе из `in-progress` снимаются `claim` и замок `.locks/<ID>.lock`.

Полной матрицы переходов нет сознательно: перетаскивание карточки законно почти
всегда, и доска не должна спорить с человеком.

**Отличие от Go:** плагин блокирует любой существующий `claim`, тогда как `tt` пропускает
claim своего агента. Это не упрощение: плагин `claim` не пишет вовсе, поэтому у человека
своего claim не бывает — любой claim на доске агентский, и трогать его нельзя.

## Запись

Идёт через `app.fileManager.processFrontMatter` — **через API Obsidian, а не мимо него**.
Именно это исключает старую проблему, когда скрипты писали в файл, открытый Obsidian,
и он перезаписывал его своей копией из памяти. Один такой инцидент перевёл 16 тасок
из `done` в `blocked`.

**Важное следствие.** Гарантия «меняется ровно один ключ, остальные байты не трогаются»
относится только к Go-писателю. Плагин её не даёт: `processFrontMatter` владеет
сериализацией всего блока и переписывает его целиком — инлайновые списки разворачиваются
в блочные (`tags: [a, b]` → три строки), лишние кавычки снимаются.

Проверено на живых данных, что это **только косметика**: заголовок с `": "` внутри
остаётся закавыченным, то есть сериализатор ставит кавычки там, где без них YAML
сломается. Под угрозой были 612 тасок с такими заголовками — ни одна не пострадала.

Цена принята сознательно: писать мимо Obsidian значило бы вернуть тот самый класс аварий.

## Замок

`.locks/<ID>.lock` — не мьютекс на время операции, а долгоживущий признак «таска
в работе», парный статусу `in-progress`. Ставится при взятии в работу, снимается при
уходе из него. Проверяется через `adapter.exists` и носит совещательный характер:
атомарности от Obsidian не требуется и не предполагается.

## Тесты

```bash
npm test        # чистые модули: схема, лейны, guard'ы
npm run typecheck
```

Тестируются только модули без импорта `obsidian`: `schema.ts`, `lanes.ts`, `guards.ts`.
`write.ts`, `board.ts` и `main.ts` состоят из вызовов Obsidian и проверяются руками —
заглушка `App` проверяла бы заглушку.

Граница проведена по одному признаку: **модуль, импортирующий `obsidian`, не содержит
логики**. Если в тест понадобилась заглушка `App` — граница поехала.

## Ограничения

- Таски с непарсящимся фронтматтером на доске не видны: Obsidian не кладёт их
  в `metadataCache`. Их показывает `tt doctor` — в vault таких 31.
- Плагин не создаёт таски и не пишет `claim`; это работа `tt` (`tt new`, `tt claim`
  появятся на этапе 4).

## Сверка с CLI

Числа на доске должны сходиться с `tt list` за вычетом непарсящихся:

```bash
tt list --vault "<vault>" --project <имя> | wc -l          # всего
tt list --vault "<vault>" --project <имя> | grep -c BROKEN # из них не видны доске
```

Замер на 2026-08-31: всего 1277 тасок, непарсящихся 31, на доске ожидается 1246.
В `webapp`, `crm` и `shop` непарсящихся не осталось вовсе.
